# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What Tikai is

Tikai (ticket + AI) is an open-source, non-profit app that combines a **ticket system** (in the spirit of YouTrack) with **git**, so AI agents can develop quickly while humans stay firmly in control.

Core ideas:
- Tickets are where work starts: an agent picks up a ticket, works on a branch, and the result is linked back to the ticket.
- **Multi-agent support**: several agents can work in parallel, and an agent can **ask a human** a question from inside the ticket instead of guessing.
- **Strong human code review** is a core feature, not an afterthought. AI-written changes are always reviewed and approved by a human before they merge.

## MVP scope

- **Claude Code is the only agent** in the MVP. Tikai orchestrates Claude Code and does not build its own agent.
- Users **bring their own LLM API key**. Tikai never ships or proxies a shared key.
- Self-hosted: the whole stack starts with a single `docker compose up`.

## Tech stack

- **Backend:** .NET (C#)
- **Database:** PostgreSQL
- **Frontend:** React + TypeScript
- **Deployment:** Docker Compose, Linux containers

## Platform requirements

- The main developer works on **Windows**. Everything (builds, scripts, tooling, docker compose) must work on Windows with Docker Desktop running Linux containers.
- Prefer cross-platform tooling: `dotnet` CLI, npm/pnpm scripts, or PowerShell-compatible commands. Avoid bash-only scripts unless there is a PowerShell equivalent.
- Mind line endings (`.gitattributes`) and path separators.

## Licensing and contributions

- License: **AGPL-3.0** (see `LICENSE`).
- Contributions use the **DCO** (Developer Certificate of Origin): commits are signed off with `git commit -s`.
- **No per-file license headers.** The root `LICENSE` file covers the whole repo.

## Working conventions for Claude Code

- Keep changes small and reviewable. One ticket or concern per branch/PR.
- Never commit secrets or API keys. Use environment variables / `.env` files, which are git-ignored, and provide `.env.example`.
- Ask when a requirement is unclear instead of guessing. This mirrors the "agents ask humans" principle of the product.
- When adding a dependency, note why in the PR description.

## Planning docs (`aidocs/`)

- `aidocs/` holds the local, git-ignored working docs for building Tikai. **Read `aidocs/design-doc.md` before starting any feature work.** It is the source of truth for architecture, data model, MCP tools and the MVP phases.
- Tikai is built in small steps, not all at once. Work on one item from "MVP phases" at a time, with a plan in `aidocs/plans/` (see `aidocs/README.md`).
- Don't implement features from later phases unless asked.

Auth: ASP.NET Core Identity with a cookie (`tikai.auth`). The first sign-up becomes admin, then sign-up closes. Every unsafe `/api` request needs the antiforgery header `X-XSRF-TOKEN` (value from the `XSRF-TOKEN` cookie set by `GET /api/auth/antiforgery`; fetch it again after login and logout). New API endpoints go under the `/api` group so they get this check.

Git: every git call goes through `GitService` (never `Process.Start("git")` elsewhere): argument lists, `--git-dir`, no system/global config, no prompts, `GIT_ALLOW_PROTOCOL` from `Tikai:Git:AllowedProtocols`. Credentials only through env (`GIT_CONFIG_*` extraHeader, `GIT_SSH_COMMAND` with a temp key file), never in arguments, URLs or repo config. Mirrors live at `<data>/repos/<project-id>/<repo-id>.git` (paths from ids only); remote branches in `refs/remotes/origin/*`, the hub's own branches in `refs/heads/*`. Writes to mirrors go through the `git` job queue.

Secrets: `Tikai:EncryptionSecret` (`TIKAI_SECRET` in compose, 32+ characters) encrypts the Data Protection key ring; the hub refuses to start without it or with the wrong one (`Security/KeyRingStartup`). `appsettings.Development.json` has a development-only secret. Stored secrets (git credentials, LLM keys) go through `ISecretProtector` with their own purpose string, are write-only in the API, and never appear in logs (`ToString` of credential and connection records hides them). LLM calls go through `IChatClientFactory`, never `new AnthropicClient()` elsewhere (it would read `ANTHROPIC_*` env vars).

Projects: archived (`projects.archived_at`, `POST …/archive`, undone by `/restore`) or deleted with everything (`POST …/delete` with the project's `name`, 202; `deleting_at` until it is gone; there is no plain `DELETE`). Both set the flag first, then stop the project's previews and cancel its active runs (`ProjectLifecycle`; 409 while a change set is delivering). A flagged project starts nothing: new tickets, runs (also retry), repositories, fetches and remotes answer 409 (`ProjectEndpoints.Closed`; `RunService.StartAsync` re-checks with the project row locked `FOR SHARE`), the fetch scheduler skips it and the inbox hides its items; everything stays readable. `ProjectDeletionHandler` stops what is left, then waits (it re-queues itself, 1 s at first, then 30 s) until no run is active and every run and preview has `cleaned_at` (the cleanup jobs need the rows; not waited for with `Tikai:Docker:Enabled=false`), deletes all rows in one transaction (children first, raw SQL, project row locked) and queues the git `delete` job per repository. Only the hub's mirrors go; a remote is never contacted. A new table that hangs on tickets, runs, change sets or repositories needs a line there. A repository with runs or change sets is not deleted on its own (409 "The repository has history"); a ticket with runs stays refused (audit trail). Web: `ConfirmDialog` with `typeToConfirm`, `isOpen` in `projects.ts`, archived projects behind "Show archived".

Tickets: numbers come from `TicketNumbers.NextAsync` inside the insert transaction (never `MAX()+1`) and are never reused. Ticket markdown is rendered only through `web/src/tickets/Markdown.tsx` (raw HTML dropped, unsafe URLs blanked; no `dangerouslySetInnerHTML`). Criteria keep their ids across edits; review coverage will reference them. Refine spec (`refine-spec.v2`) sizes the ticket first; `SpecRefiner.Map` enforces the size's limits (criteria on the whole ticket, questions, assumptions, description only for medium and large) and keeps only what differs from the draft: criteria are rewrites (`replaces` = place in the request's criteria) or new, questions have 2–3 options. The web writes the proposal straight into the form (`tickets/refine.ts`): a rewritten criterion keeps its row and id, assumptions and decisions go under `## Assumptions` in the description; each change is marked under its field with an x that puts it back, a field edited by hand loses its mark, "Undo refine" restores the form, "More detail" refines the original form again with `minSize`.

MCP: `/mcp` is stateless Streamable HTTP (protocol 2026-07-28) and accepts only a run token (`Authorization: Bearer tikai_run_…`, scheme `RunToken`; the login cookie is ignored there, and the token does not open `/api`). Tokens come from `RunService` (stored as SHA-256 only; invalid once the run has ended; `RenewTokenAsync` replaces one). Tools take no run, ticket or project ids: everything comes from `RunScope`. Tool argument names are snake_case (the C# parameter names); errors the agent can fix are thrown as `McpException`. What people read is capped in `AttentionRules` (plan: summary ≤ 160, 1–6 steps, ≤ 3 risks; question: ≤ 200, 2–4 options plus a required `recommended`, context ≤ 2 000; self-report: summary ≤ 400, notes ≤ 200, ≤ 3 open concerns); an error names the field, the limit and the length, and the inbox shows the headline with the rest behind a `Disclosure` (`web/src/ui/layout.tsx`). Blocking tools (`ask_human`, `propose_plan`) create or merge an attention item (same run, latest blocking item, same request hash → reused, stored answer returned at once) and wait through `IAttentionWaiter`, which registers before it reads the row; a progress notification and a re-read every `Tikai:Mcp:HeartbeatInterval` (30 s). The database is the source of truth for answers; nothing in memory must survive a restart. Preview file tools (no state, nothing stored): `get_preview_spec` returns `docs/preview-file.md` (embedded in `Tikai.Api`, `Previews/PreviewSpec`; the hub image copies that file into its build) and `check_preview_definition` (argument `content`) runs `PreviewDefinition.Parse` on the text and returns `result` (`valid` or `invalid`) with `errors` (`key`, `line`, `message` from `PreviewDefinitionParse.Problems`; a missing key has the line of the mapping around it); an invalid file is a result, not a tool error. The start prompt (`run-start.v4`) and the summary prompt (`run-summary.v3`) ask for the check before `submit_for_review` whenever the file changed; both also describe the sandbox (no root or apt, `/tmp` noexec, tools under `$HOME`, no Docker, no browser).

Runs: `POST /api/projects/{slug}/tickets/{n}/runs` creates a queued run (one active run per ticket and per repository, enforced by partial unique indexes) and a `runs` job. `RunStarter` bundles the default branch in the mirror (the only git the hub runs), writes the run directory through the Docker archive API into a never-started `seed` container (tar headers set owner and mode: run root, `mcp.json` and `.tikai/ticket.md` root-owned and read-only; `work/`, `home/`, `claude/` owned by uid 1000), clones in a `prep` container (agent image, agent uid, no network), renews the token, and starts the agent. The hub never mounts the runs volume and never runs git or follows symlinks in a run directory; the subpath mount is exactly the run's GUID. The sandbox (user, read-only root, cap-drop, limits, network, `json-file` log driver) is set only in `DockerContainerRuntime` (`CreateAsync` for runs, `CreatePreviewAsync` for previews, one `Sandbox` builder); adapters and preview definitions give image, command and environment. State changes are compare-and-set along `RunStateMachine`; a container's end goes through `RunExit.Map` (exit code 0 alone means nothing; the `system/init` MCP status is checked as soon as it arrives). Agent output is redacted (`SecretRedactor`) and trimmed (`RunEventPayload`) before it becomes `run_events` (`StreamJsonParser` drops bookkeeping lines like `thinking_tokens`, gives a task the agent put in the background one line at its start and end (Claude Code reports most longer Bash calls as tasks too; those give none) and keeps other unknown lines raw with their type), numbered from `agent_runs.last_event_seq`; after a hub restart the monitor re-reads the log and skips `log_lines_read` lines. Docker log timestamps are not used (Docker splits long lines into 16 KB chunks, each with its own timestamp).

Pause and resume: a run is `blocked` while one of its blocking items is open (`AttentionService.RaiseAsync` blocks it in the transaction that locks the run row) and runs again only when the agent has every answer (`delivered_at`: set by the tool that returns it, or by the resume start), not when it is stored. A container end while blocked keeps the run blocked without a container (`EndAsync` with `Block` on a blocked run); an answered but undelivered item maps to `Block` too. A resume is requested (`RunResumes.RequestIfReadyAsync`, run row locked, at most one live `runs` job per run) by the answer, by a container end and by the reconciler: blocked, no container, nothing open, no cancel. Every end is container-scoped (`RunEnd.ContainerId` must be the run's `container_id`). The resume renews the token, rewrites only the adapter's root-owned files (`mcp.json`) through a seed container, reads session file, `git log` and `git status` in an `inspect` container (session line first, sections split by a random marker), then starts `--resume <session_id>` with `run-resume.v1` or a fresh session with `run-summary.v3`; a resumed container that ends with an agent error is retried once as a summary (`RetryWithSummary`). The block timeout counts from the oldest open item's `created_at` by the database clock (`now()`), checked by the reconciler; `ToolCallTimeout` must be at least `BlockTimeout` + 15 min. Ending a run dismisses its open blocking items (answering one is 409) and its open review and conflict items (`RunStore.EndLockedAsync`; a cancel from the board gives no verdict). Every run that ends queues the cleanup of its directory (Delivery, below). Row locks: `SELECT 1 … FOR UPDATE`, not `FromSql("SELECT * …")` (the entities map `xmin`).

Live updates: SignalR hub `/hubs/live`, login cookie only (a run token gets 401), requests with a foreign `Origin` get 403, no hub method changes data (actions stay REST with antiforgery). Messages carry ids and keys only (`RunChanged`, `AttentionChanged` to groups `all` and `project:<id>`; `RunEvents` to `run:<id>`; `Resync` after the event bus reconnected); the browser re-reads through the REST API. Groups are per connection: the client re-sends its watches after a reconnect and re-reads what it shows. The live log asks `GET /api/runs/{id}/events?afterSeq=<last>` and drops seqs it has; seqs become visible in order (the counter row lock is held until commit), so there are no gaps. New views that change live: add their query keys to `staleKeys`/`liveKeys` in `web/src/live/live.ts`.

Run cost (`RunCost.After`): `cost_usd` is the agent's session total (Claude Code's `total_cost_usd` covers a resumed session's earlier containers, checked with a real run) plus `cost_usd_before_session` (earlier sessions, set when a summary attempt starts); `cost_tokens` adds each container's tokens, summed from per-message `usage` (the result's `usage` covers only the last process).

Reviews: `submit_for_review` does the git part inside the tool call (`ReviewSubmissions`): a `bundle` container (agent image, agent uid, no network) bundles the run branch from the run's `base_sha` in `/run/home/.tikai-review/`, the hub downloads it through the archive API of the stopped container (copied to a file first: `TarReader` on Docker.DotNet's chunked stream fails), accepts exactly one regular file within `MaxBundleBytes`, and imports it with `bundle verify` and `index-pack --strict --fix-thin` on the bundle's pack (not `fetch` with `fetch.fsckObjects`: git before 2.46 skips that for bundles, and the hub image has 2.43) into `refs/heads/<run branch>` and the pinned `refs/tikai/rounds/<change-set>/<n>`, holding the repository's `MirrorLocks` (the git job handler holds it too). Base = merge base with the default branch. Then, with the run row locked: change set (one per run), round (self-report, uncommitted files), run `running → in_review` (container still attached), ticket `in_review`, review item. Agent-fixable problems (no commits, bad bundle) are tool errors. A container end of an in-review run keeps it in review (`RunExit.KeepsReview`); only a cancel ends it. Diffs and contents are computed in the mirror per request (`diff-tree -M`, blob ids from the diff, never from the client). Viewed state stores the file's blob id (`ReviewRules.ViewKey`), so a changed file shows unviewed in a later round without a reset. Verdicts: reject (cancels the run, closes the change set), request changes (below) and approve (Delivery, below).

Comments and fix rounds: a thread belongs to a change set and the round it was started in, anchored to a line range on one side of a file (`old` = the round's base, `new` = its head; checked against the blob: a text file with those lines) or general (no anchor). Comments are `note` (humans only) or `send_to_agent`; they are visible to people at once, and a `send_to_agent` comment reaches the agent only with request changes (`sent_at`), editable and deletable by its author until then. People resolve and reopen threads; the agent only replies. Request changes (409 when nothing would be sent) sets the verdict, turns an optional message into a general thread, marks the unsent comments of open threads sent, moves the run `in_review → changes_requested` and the ticket back to in progress, dismisses the review item, all with the run row locked; an attached container is stopped (`RunControl.StopAsync`). `RunResumes` treats `changes_requested` like a blocked run (no container, no live job, no cancel → a `Resume` job); a container end keeps it (`RunExit.KeepsChangesRequested`), and the reconciler resumes it too. The resume gets `ResumeInfo.Changes` (the latest round's verdict): `--resume` with the `message` of `run-changes.v1` (answers to questions come first), or a fresh session with its `prompt`. `get_review_comments` returns open threads with sent comments (only the sent comments and the agent's own replies); `reply_to_thread` adds a redacted agent comment while the run is running. The next submission is round n+1 of the same change set; its result says how many threads have no reply. `RunEndContext.Submitted` is "the run is in review" (an earlier round's review item does not count). Interdiff (`ReviewDiffs`; files, file and viewed take `full=true` for the whole change): same base → `diff-tree` of the two heads; changed base → the files whose patch differs (`Interdiff.SamePatch`: no index line, no hunk line numbers), each with its whole change. In the interdiff the left pane is the previous round's head, so its `new`-side threads show there; other threads are listed above the file. The analysis of a later round with the same base and a done analysis of the round before uses `review-analysis-interdiff.v3` (interdiff patches, previous analysis, sent threads and replies; tier from the interdiff unless the whole change has a strict path; `ReviewAnalysis.InterdiffSince`), else the full v1. Web: threads have their own query key (`change-set-threads`, in `staleKeys`/`liveKeys`).

Delivery (approve): `projects.settings.delivery` picks the mode (`merge`, default, or `push_branch`) and the merge style (`squash`, default, or `merge_commit`); a repository without a remote always merges in the hub. Approve (`ApproveAsync`, run row locked): the latest round gets the verdict, the change set goes `open → delivering`, review and conflict items are dismissed, a `deliver` job goes on the `git` queue (one at a time with clones and fetches, under `MirrorLocks`); the run stays `in_review` (cancel is refused while delivering) and an attached container is stopped. `ChangeSetDelivery`: merge = `git merge-tree --write-tree` onto the target (no worktree; with a remote the target is `origin/<default>` after a fetch), `commit-tree` (squash: one parent; merge commit: two) with the agent profile as author, the approver as committer and `MergeMessage` (ticket subject, the agent's summary without trailer lines, `Ticket:` and `Co-authored-by:` trailers); with a remote it pushes `<commit>:refs/heads/<default>` without force first (a rejected push fetches and merges again, 3 times) and only then moves `refs/remotes/origin/<default>` and `refs/heads/<default>`, so the hub never holds an unpushed merge; without one it updates `refs/heads/<default>` compare-and-set; the run branch ref is deleted, the round refs stay. Push-branch mode pushes the round head to `refs/heads/<run branch>` (no force). Success, run row locked: run `in_review → merged | pushed` (`RunTrigger.Merge | Push`; `pushed` is an ended state), change set `merged | pushed` with `delivered_sha`, ticket `done`, open items of the run dismissed, a cleanup job. A conflict reopens the change set (verdict cleared, `delivery_error`) and raises a `conflict` item (`ConflictPayload`: round, default branch, files); `POST /api/change-sets/{id}/rebase` is request changes with a generated message and `review_rounds.rebase_requested`, so the resume gets `ReviewRequest.Rebase` (default branch, files), `RunStarter.ResumeAsync` writes the default branch as `prep/default.bundle` (root-owned, read-only; `/run/prep/default.bundle` for the agent) and the adapter uses `run-rebase.v1`. A failed push (`GitException`) is retried by the queue (3 attempts, `delivery_error` shows the attempt); after the last one the change set reopens and a review item comes back with the error (`AttentionItemInfo.DeliveryError`). Repositories: `PUT …/repositories/{id}/remote` (`GitService.ConnectRemoteAsync` under the mirror lock: fetch, push the default branch when the remote is empty or behind, refuse a diverged or foreign history and restore the old remote); `GET …/repositories/{id}/bundle` (default branch with HEAD, temp file deleted on close). Cleanup: every run that ends queues a `runs` job of kind `Cleanup` (`RunCleanups.EnqueueAsync`; `RunCleanup` removes the run's containers, then runs a `cleanup` container: root, only `CAP_DAC_OVERRIDE`, no network, the whole runs volume, `rm -rf -- /runs/<guid>`) and sets `agent_runs.cleaned_at`; the reconciler queues it for ended runs still uncleaned and never removes a cleanup container.

Previews: `tikai-preview.yml` at the repository root (agent-written, so untrusted) is parsed by `PreviewDefinition` into the hub's own model (setup steps, apps, services, `idle_minutes`; unknown keys, anchors and several documents are errors; `app` is one app named `app` on `/`, `apps` a map of up to 5 with a `path` prefix each, exactly one on `/`, no name shared with a service) and never handed to Docker; a change to it is a strict path in the analysis. Start (`POST /api/change-sets/{id}/previews`, latest round, the checked text stored on the row; under one advisory lock: the change set's active preview is stopped as replaced, at most `Tikai:Previews:MaxRunning` active) queues a `previews` job (one attempt): `CreateRefBundleAsync` of the round ref, a seed container writes `previews/<guid>` (own volume, subpath = GUID, the hub never mounts it), a prep container (agent image, no network) checks it out to `/preview/src`, each setup step runs in its own sandboxed container on the agents network (internet for registries), then the network `tikai-preview-<id>` (internal), services (image user, cap-drop ALL plus `ServiceCapabilities`, Docker health check) and then all apps (each `tikai-preview-app-<id>-<name>` with its name as network alias; agent uid, run sandbox; a `generate` value is random per preview, the same in every app that lists it, only in memory and redacted from the log); running once every app passes its health check, failed by the reconciler when any app stops. The hub reaches each app by joining that network (`Tikai:Previews:HubContainer`) or, for a hub on the host (dev, integration tests), through a loopback port per app (`Upstream=Loopback`, then the network is a normal bridge); `previews.upstreams` (jsonb: name, path, url, container id per app) is set when it runs. States `preparing | starting | running | stopped | failed` change compare-and-set; every stop and failure queues a `preview_stops` job (containers, network, then the `cleanup` container; `cleaned_at`). Stops: button, a newer preview, idle (`last_request_at`, written by the proxy at most once a minute), `MaxLifetime` (4 h), change set merged, pushed or closed (`PreviewStops.ForChangeSetAsync` in the delivery and run-end transactions, and the reconciler). Preview log: `preview_log_lines` numbered from `previews.last_log_seq` (sources `hub`, `setup <n>`, `app` or `app <name>`, a service's name; every app's log is followed); `PreviewChanged` (groups `all`, `project:<id>`) for state and log, web key `change-set-preview` (the log's key follows `lastLogSeq`). Access: `PreviewProxy` runs first in the pipeline; `<32-hex id>.<suffix>` (`Tikai:Previews:Domain`, else `preview.localhost` and only for a hub opened on localhost) never reaches the hub's routes; `POST /api/previews/{id}/entry` gives a one-time link (`preview_entries`, SHA-256, 2 min) that `/__tikai/enter` trades for a host-only `tikai_preview` cookie (Data Protection, time-limited); requests go to the app with the longest matching prefix (`PreviewHosts.Route`, path unchanged) through YARP's `IHttpForwarder` without any `tikai*` cookie. `Tikai:Docker:Enabled=false` (a hub without Docker, e.g. Tikai's own preview) turns runs and previews off and says so.

Review analysis: the submission transaction sets the round's `analysis_status` to pending and queues a `reviews` job (`ReviewAnalysisJobHandler`). The job uses the run's own provider, picks the tier with `AnalysisTiers` (strict and light globs are constants until trust rules exist) and the model from `projects.settings` (`ProjectSettings`; defaults per tier in `ReviewModels.Default`), reads patches with `IGitService.PatchAsync` (no external diff or textconv, literal pathspecs, byte cap) within `AnalysisInput.PatchBudget`, calls `ReviewAnalyzer` (`review-analysis.v3`: a one-sentence `headline` and at most 3 `look_at` places first, only medium and high risks, the summary last as details), and stores what `AnalysisCleaner` keeps (known criterion ids and paths only; headline ≤ 160, look_at lines of text files that exist after the change; every reviewable file in exactly one group) as `review_rounds.analysis`. Transient provider errors throw so the queue retries (3 attempts); everything else, and the last attempt, ends as `failed` with a message, and a failed analysis never blocks the review. The run's answered questions and plan decisions go in as `<decisions>` (`AnalysisContext.Decisions`, oldest first, dismissed ones left out; at most 10, the newest, each text cut; not from the patch budget): work a person asked for is in scope, a criterion an answer changed is judged as changed. Everything the agent wrote goes into the model's input inside tags the prompt calls data; the web shows the model's texts as plain text. Retry: `POST /api/change-sets/{id}/rounds/{n}/analysis`. The analysis is not part of the run's cost. `Tikai:Llm:AllowHttpBaseUrls` lets provider base URLs use http (integration tests and the e2e stack use it). Web: files and contents have their own query keys (`change-set-files`, `change-set-file`), so live updates of `change-sets` do not refetch them. Rows without `headline` and `look_at` are v1 and still shown. With a done analysis the review screen and the inbox card merge the agent's self-report into it: headline, one verdict line (`verdictLine`: "Meets 4/5 criteria · 1 partial · 2 files need a close look"; close look = look_at or high risk), the places, criteria that are not covered (covered ones in one line, the agent's claim only where it differs), summary and the agent's report under Details; uncommitted files stay in sight.

Inbox: open items, blocking (an agent waits) first, then newest. Questions and plans are answered (`/answer`), failures and reviews without an open change set dismissed (`/dismiss`; a review with an open change set gets a verdict instead; `AttentionItemInfo.ChangeSetStatus` tells the card which), failures retried (`/retry`: a new run with the same repository and provider); starting a run dismisses the ticket's open failure items. Blocking items are never dismissed by people (cancel the run).

Web UI: build screens from `web/src/ui/` and the theme's colour names (never hex values or Tailwind's default palette, which is off); colour only where it means something (amber = an agent or a review waits for a person, blue = running, green = done, red = failed); no gradients, card shadows or emoji. Accessible names are what the Playwright test finds (`Inbox, N waiting`, article labels like `Plan to approve: KEY-1`, `Changed files`, `Verdict`); keep them, or change the test with them. Confirmations use `ConfirmDialog`, not `window.confirm`.

Prompts: one versioned markdown file per prompt in `src/Tikai.Llm/Prompts/` (`refine-spec.v2.md`) or, for agents, in the adapter (`src/Tikai.Adapters.ClaudeCode/Prompts/run-start.v1.md`); a changed prompt is a new file. Structured output uses an explicit JSON schema with a `required` list: the Anthropic SDK silently drops a schema without one (no `output_config` is sent), and schemas inferred from classes with settable properties have none.

Project references: `Core` references nothing; `Data`, `Git`, `Llm`, `Review`, `Orchestrator`, `Mcp` and `Adapters.ClaudeCode` reference only `Core`; `Api` references everything. A new `src` project needs a rule in `tests/Tikai.ArchitectureTests/ProjectReferenceTests.cs`.
